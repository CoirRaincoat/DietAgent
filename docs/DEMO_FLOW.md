# 比赛 Demo 演示流程

## 准备

按 README 一键启动前后端，打开 `http://localhost:8080/demo`；自由对话页面为 `/`，API调试为 `/docs`。GET /health 应为 ok、recipe_count=2000、profile_count=3、profile_data_scope=["synthetic"]；GET /demo/profiles 查看合成画像。原始健康资料仅用于本地验收。

自动演示：

```powershell
.\.venv\Scripts\python.exe -m evaluation.demo_http --base-url http://localhost:8080
```

脚本只使用合成用户900001和自造消息，自动延续session_id，为每次演示生成新request_id。服务需配置有效DeepSeek密钥。

## 三分钟浏览器演示

1. 进入 `/demo`，点击“减脂晚餐”，展示Agent主动询问人数与忌口。按按钮逐项回答；遇到未知过敏原等开放问题时，在输入框补充具体信息。
2. 菜单生成后，点击“查看做法与来源”，展示原始配料、步骤、菜谱行号和指纹；关闭详情后点击“换一道”，观察指定位置变化。
3. 打开“营养分析”，展示实际食材来源、目标匹配与风险；热量和营养量显示数据不足。
4. 点击“灵活换菜”启动新会话，再点击“整餐不吃鱼，重新安排”；或选择“记住忌口”，补充“不能吃辣”，查看新约束和实际返回菜品。

三个案例均使用合成用户900001，结果来自实际后端；点击新场景会重置旧会话。出现网络错误时用“重试这次请求”，保留原请求ID；可以重新开始。没有编造菜单、工具动画或营养分数。

## 澄清 → 菜单 → 换菜 → 解释

| 轮次 | 输入 | 展示重点 |
| --- | --- | --- |
| 1 | 帮我安排一餐。 | 询问人数、餐次、忌口；菜单为空，没有规划工具执行 |
| 2 | 2个人，晚餐。 | 只继续询问忌口，保留已确认信息 |
| 3 | 没有其他忌口，不吃辣椒，安排三道菜。 | 三张真实菜谱卡片、配料/步骤、来源指纹、营养和风险 |
| 4 | 只替换第二道菜，其他保持不变。 | 第一和第三道保持，只有第二道变化 |
| 5 | 解释刚才这份菜单。 | 菜单保留，tool_calls没有menu_modify；解释来自可核查事实 |

手动POST首轮：

```json
{"user_id":900001,"message":"帮我安排一餐。","request_id":"presentation-1"}
```

后续携带返回的conversation_state.session_id，并使用新request_id。新演示请新建会话与请求ID，避免旧状态或重试缓存影响展示。

## 补充场景

- 900002：新会话输入“1人晚餐，三道菜，按档案忌口”。展示海鲜/花生过敏继承、库内筛选、控糖目标匹配与配料风险，不宣称血糖效果。
- 900003：新会话输入“1人晚餐，三道菜，没有其他忌口”。展示降压偏好的配料解释与护心目标的insufficient_data提示。

## 验收问题

- 菜品是否编造：展示recipe_id、provenance.source_row、fingerprint与原始配料/步骤。
- 营养是否编造：展示真实食材贡献与不足说明，没有精确营养量或效果评分。
- 是否具有状态：页面展示确认状态和已记录约束；完整confirmed_fields、pending_fields、constraints与revision可在/docs的API响应或自动验收报告核对。
- 工具是否执行：页面展示实际执行的工具名称；完整事件和计数可在API响应核对。澄清时不规划，解释时不换菜。
- 真实资料是否外传：默认接口仅合成画像，适配器阻断original；真实验收由封锁网络的测试覆盖。

50份档案及原始20组对话本地共179轮，0断言失败；信息不足时正确澄清。人工Intent只验证后端业务与数据，不能证明真实NLU准确率。真实模型合成五轮是接入与流程证据，不代表比赛全量准确率或正式延迟达标。

v0.3.0已提供Vue用户界面、菜品详情、澄清按钮、换菜与营养来源卡片。菜品图片使用标明非实拍的示意占位，份量和定量营养仍待数据完善。浏览器Mock验收与真实模型验收分别记录于DEMO_V030_REPORT.md。

真实联调中发现“减肥”可能被模型原样返回而未归一到已支持的“减脂”。内置减脂案例使用明确术语“最近想减脂，帮我安排晚餐”；自由输入同义词的归一能力留待Phase 11单独评测，未支持目标继续显示提示，不当作健康匹配成功。
