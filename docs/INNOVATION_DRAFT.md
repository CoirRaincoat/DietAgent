## 目前有实现依据的系统设计

1. **按人归属、按整桌执行的约束状态。** 对话中分别保存每位用餐者的过敏、忌口、别名和是否参加，再把在场成员的硬约束合并到共享菜单。成员退出时不再贡献本餐约束，重新参加时原事实仍在；过敏原或人数不明确时先澄清。实现见 app/agent/diners.py、app/agent/service.py，行为测试见 tests/test_agent_api.py 和 tests/test_review_state.py。它解决的是多人共餐时限制归属及跨轮保留问题，不能据此宣称未知成员已被安全覆盖。
2. **来源可查的安全规划与受约束解释。** 菜单来自有稳定 ID 的菜谱库，规则和规划器检查成菜资格与已知限制；解释只使用程序确认的事实，文本接口逐道输出已验证菜品。回归验证器另读本地源菜谱，对菜单和替换建议核对 ID、来源行、指纹、原料与步骤，不接受服务自报“通过”作为独立证据。实现见 app/rules/engine.py、app/agent/service.py、evaluation/regression_suite.py。食材词表有限，现阶段只提供定性营养说明。
3. **有记忆的局部重规划。** 指定换菜尽量保留未受影响槽位；整份否定累积拒绝菜谱和同名变体；新增食材偏好在有界范围内补足，已经满足时不强行换菜。实现见 app/agent/planner.py、app/agent/service.py，回归见 tests/test_preference_updates.py、tests/test_rejection_memory.py。目前没有证明所有菜单上的全局最少修改。
