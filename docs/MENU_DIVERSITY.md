# 安全候选内的菜单多样性试验

本改动只重排**已通过菜谱资格、过敏、忌口和全桌限制筛选**的候选，不扩大可用菜谱集合。它不改变菜数、汤数及已确认的有效菜位；用户指定换菜时，其他有效菜位照旧保留。

## 选择顺序

每个空位沿用原有优先级，再在同等条件下比较多样性：

1. 整桌类别、做法及冷热文字证据的现有 `balance_rank`；
2. 健康目标与明确食材偏好的规则分；
3. 与本轮请求及既有偏好相同口径的检索相关性；
4. 已选菜品之间的源食材集合重合度、首个食材是否相同、做法重合度、菜名相似度；
5. 原检索顺序和 `recipe_id`，保证同样输入得到同样结果。

前三级有差异时，多样性**不能**让低优先级菜品反超。只对最早的 64 个同分候选计算较贵的相似度；检索相关性先在全部同分候选中计算，再截取候选池，避免遗漏较晚出现的明确命中。相同菜名仍由原规划器去重；同主料不同做法仍视为食材重复，不同主料相同做法仍有轻度做法重复。缺少食材或做法元数据不当作“完全不同”。

这些值来自菜谱文字和启发式标签，只用于排序；不是过敏安全、营养含量或实际出餐温度的证据。最终菜单仍执行原有逐菜规则校验。

## 合并前对照

分别在 PR10 合并版本和此分支上运行同一套一体化自测，固定模型配置、合成用例 SHA-256、菜谱 CSV SHA-256 和运行机器。保存两份 `regression/report.json` 与 `report.md`，比较：

- 硬约束与来源检查失败数、功能场景通过数、已确认菜位的最小修改；
- `summary.menu_quality` 的类别覆盖、做法种数、冷热证据与食材重合度，同时检查逐场景变化，不只看平均值；
- 客户端 TTFT、单轮端到端和多轮平均耗时的有效性及分布。

若安全性或最小修改退步、质量收益不明显，或性能恶化，则不合并此排序改动。单测通过或一次菜单样例变好，不等于这些条件已经满足。私有 50×20 矩阵仍需单独运行且只提交脱敏汇总。
