## 三、推荐评测入口：POST /chat

Content-Type 为 `application/json`。首轮请求：

```json
{
  "user_id": 1,
  "message": "合成测试：1人晚餐，三道菜，没有其他忌口。",
  "request_id": "synthetic-case-01-turn-01"
}
```

| 字段 | 实际约定 |
| --- | --- |
| user_id | 必填整数；正式云目录为 1-50，不由模型选择身份 |
| message | 当前新增的一轮纯文本，去首尾空白后 1-2000 字符 |
| session_id | 首轮省略；后续使用响应中的 32 位小写十六进制值 |
| request_id | 可选业务幂等键，1-128 字符；新操作用新值 |

响应核心字段为 `status`、`menu`、`reason`、`warnings`、`conversation_state`、`clarification_questions`、`replacement_suggestions`、`nutrition_analysis`、`explanation_source`、`timings_ms` 和 `schema_version`。菜单卡片包含菜谱 ID、原文食材和步骤、来源与指纹、定性营养和替换建议；生成方案的来源类别单独标记且 `source_row=null`，不能当作第 0 行。

缺人数、餐次、忌口等必要条件时主动澄清，菜单为空；无可行菜单时给出失败原因和保留的约束，不把旧菜单当作本轮成功结果。多人共享限制聚合后统一检查，但当前未约定通过 HTTP 自动关联多个官方档案 ID，不能假设一次请求自动识别档案中的家庭成员。

后续请求需复用 `conversation_state.session_id`，用户身份必须保持一致。相同请求在状态版本未前进时可返回原结果；复用业务 ID 修改消息、访问其他用户会话或重放旧版本会返回 409。系统保留拒绝记录、安全约束和有限历史恢复范围；不保证崩溃后的完整 exactly-once。

## 四、兼容入口：POST /v1/chat/completions

本轮遵循用户提供的最小补丁说明所记载的已交合同：保留POST、JSON Content-Type、云入口Bearer认证、固定model、user档案ID字符串及首轮省略/续轮复用会话；不修改已交PDF或令牌交付段。请求Schema必填`model/messages`，消息必填`role/content`；入口另要求至少一个合法身份位置。未发现额外必填业务字段，没有修改请求模型。档案ID映射属于本项目合同，不宣称完整OpenAI原生user语义或所有参数兼容。

最小首轮正文（所有尖括号须替换）可以只含：

```json
{
  "model": "fangtai-meal-agent",
  "user": "<已授权的测试用户ID>",
  "messages": [{"role": "user", "content": "合成示例：1人晚餐，没有其他忌口。"}]
}
```

`stream`可省略，默认false；显式true/false均支持，null不支持。`stream_options`、`context`、`request_id`及首轮会话可省略；非null的stream_options仅可在stream=true时使用，允许空对象或include_usage=false，不支持usage=true。选填不等于任意类型或空值均合法；nullable身份为未提供，仍须有其他合法身份。响应`X-Request-ID`不要求反向提供。

以下为请求格式，所有尖括号项须替换，不能原样执行；用户标识使用调用方实际获授权且目标目录中存在的测试 ID，不能猜测或默认选用某个正式用户。该 ID 可能加载预设档案并触发用户消息的模型解析，不代表档案已合成。完整身份类型、冲突规则、两轮示例与菜谱尾部解析以 [API 文档](API.md#post-v1chatcompletions) 为准。

```http
POST /v1/chat/completions HTTP/1.1
Host: <部署域名或地址>
Authorization: Bearer <PUBLIC_API_TOKEN>
Content-Type: application/json
Accept: text/event-stream

{
  "model": "fangtai-meal-agent",
  "messages": [{"role": "user", "content": "合成测试：2人晚餐，无其他忌口，安排三道菜。"}],
  "user": "<已授权的测试用户ID>",
  "stream": true,
  "request_id": "synthetic-case-02-turn-01"
}
```

`user` 为正整数 ID 的字符串，可用 JSON 正整数 `context.user_id` 或 ASCII 正整数请求头 `X-User-ID` 替代；重复位置解析后必须一致，不能相互覆盖。每次请求只接受一条新增 user 文本，服务端保存历史；不接受完整历史 messages、system/assistant 消息、图片、tool_calls 或额外生成参数。缺少全部身份位置返回422 `missing_user`，冲突返回409 `identity_conflict`。该入口是明确界定的文本子集，不能泛称支持所有 OpenAI SDK 参数。

响应提供 `X-Session-ID`；后续仅发新消息，通过正文顶层 `session_id`、`context.session_id` 或 `X-Session-ID` 复用，同一会话保持同一用户，重复位置必须一致。跨用户返回409 `session_conflict`。`request_id` 是业务幂等键，与 `context.client_turn_id`、`X-Client-Request-Id` 一致时等价；合法重放的文本保持一致，冲突或过期重放返回409。`X-Request-ID` 仅作链路追踪，不是业务幂等键。

2026-10-09 本地新增的用户选定输出约定为：保留原自然语言正文，末尾追加 `【菜谱JSON】` 和 fenced `json` 数组，每项只有 recipe_id/name，顺序与本轮最终核验菜单一致。澄清/不可行时明确“本次未返回菜单”并输出 `[]`；历史、建议和未采用生成菜不入数组，当前重新核验并保留的菜单仍入数组。ID 是项目内部标识，生成菜不冒充原库，示例及来源边界见 API 文档。该约定不声称为已核实的赛事官方强制规范，也不证明当前云版本已更新。

非流式正文及尾部位于 `choices[0].message.content`，请求只需将 stream 改为 false。SSE 使用 `data: <JSON>\n\n`，首块 role 后正文及尾部均在 `choices[0].delta.content`；所有尾部 content 完成后才发送 `finish_reason=stop` 和一次 `[DONE]`。先增量解码 UTF-8 和完整 SSE 事件，再解析外壳、拼接 content，正常完成后解析最后一个完整约定尾部，不逐 chunk 搜索。异常/取消不补造 JSON 或正常终止，HTTP 错误不当作 `[]`。

两种格式使用同一份领域结果和文本，不额外调用模型，不发送等待话术冒充最终答案。`include_usage=true` 暂不支持，不虚构 token 计量；仍是完成规划核验后分块输出，不是模型 token 实时透传，也没有本次 TTFT 改善证明。若目标地址使用 HTTP，Bearer 与正文没有 TLS 保护；本次不改 TLS 或部署。

答疑主题 34 将首 Token 定义为最终答案的第一个有效内容。当前先完成解析/检索/规划/校验，再开始流式正文；`Server-Timing` 和提供商响应耗时不是公网最终有效首 Token 时间。最终云候选需按该口径单独实测。

## 五、错误与容量

| 状态 | 含义与处理 |
| --- | --- |
| 401 | 云入口令牌缺失或错误 |
| 404 | 用户/会话不存在；不自动更换用户 |
| 409 | 身份来源冲突、跨用户会话或业务版本冲突 |
| 422 | 不支持的请求结构或字段 |
| 429 | 入口限流或后端处理容量已满 |
| 500 | 最终菜单输出数据非法，不伪装为成功空数组 |
| 502 | 模型结构化输出不符合验证要求 |
| 503 | 模型/检索暂不可用，保留已知约束 |

后端兼容入口使用 `error.message/type/param/code`；字段错误指出字段与安全修正方式，缺身份不默认选人。本地云Nginx模板的401现补齐同样四字段，保留401、`unauthorized`、原鉴权和限流，`type=authentication_error`、`param=Authorization`；没有拦截所有后端错误。历史网关仅code/message，现有云部署是否更新仍未验证。本轮2026-10-10实际Nginx 1.30.5的本地隔离nginx -t及HTTP检查已通过，仅使用假令牌与模拟后端，记录见[隔离验收报告](RELEASE_DELIVERY_20261010.md)。原生入口使用原业务错误结构。模型、检索及新增呈现校验错误在 SSE 头之前返回 JSON 错误。后端单 worker、最多 8 个处理中请求，同用户需要有序处理，不宣称已经达到某个公网 QPS。云并发和稳定性测试尚未完成。

四字段JSON保证仅适用于兼容入口已处理的应用错误及网关401，不能扩大为全部非200响应。原网关限流及其他路由、方法、代理或未捕获错误可有不同格式；调用方必须先检查HTTP状态码和Content-Type，再按实际正文解析，不把失败当作成功菜单或SSE。本轮实际429为text/html；80请求突发中22个200、58个429，限流请求未到模拟后端，冷却后恢复。这是单批本地冒烟，不是生产性能实测；静态模板或后端模拟401仍不能当作真实网关认证验收。

新增固定`GET /api-guide` JSON及同路径HEAD，后端与云Nginx源码模板路径一致；模板只公开精确GET/HEAD，其他方法405，不扩大聊天路径豁免。内容只有公开规则、占位符首轮/续轮示例、非流式/SSE和错误说明，不查档案/会话/环境/配置，不创建状态或调用模型。HEAD无正文；查询参数、用户头和认证头不回显，正常推荐content不夹入协议说明。本文描述冻结候选源码；具体运行环境是否开放，以该环境实际网关版本为准，本轮未探测服务器。

## 六、技术路线与隐私边界

处理链为：用户输入 -> 受 Schema 限制的意图解析 -> 本机会话/多人约束更新 -> 菜谱检索 -> 独立规则过滤 -> 组合规划或受限换菜 -> 来源/安全复核 -> 定性营养与本地解释。

四类工具分别为 `recipe_search`、`health_check`、`menu_modify`、`nutrition_analysis`。模型负责理解新增用户消息，不直接决定最终菜谱或修改用户身份；规则处理过敏、忌口、餐次、数量、做法及其他硬条件，无法满足时澄清或说明不可行。内部评分只是菜单选择的代理信号，不是营养浓度、临床功效或官方评分。

原菜谱保留原文、来源行和内容指纹；成菜主角色与食材营养贡献分开，蔬菜主体可能包含肉类配料，不能据此保证素食或个人蛋白质摄入。做法识别采用原步骤的有限证据，器具、调汁、拌馅不自动成为整菜做法；证据不足保持未知。

定性营养输出包括蛋白质、碳水、脂肪来源、膳食纤维、食材贡献、目标匹配及风险。份量、品牌、分餐量和营养表不充分，因此不输出虚构克数、能量、钠含量或达标保证。明确过敏是硬拒绝，不能靠定性健康排序绕过。

原档案、体检数据、身高体重、派生本地健康约束、成员信息、源菜谱和助手解释不发送给模型。模型输入使用用户自写文本、用户消息历史和受限结构字段；局部授权和完整安全状态仍在本机验证。用户主动写入聊天的敏感内容属于用户消息，本系统不能宣称“任何用户健康文字均不出网”。解释由本地已验证事实生成，无额外解释模型调用；有限付费菜谱提案在当前云配置中关闭。
