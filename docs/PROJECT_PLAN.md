本项目建设一个能够理解用户健康档案和连续对话、从菜谱库中规划菜单、处理多人约束并解释修改原因的膳食规划 Agent。初评交付重点是可调用的完整系统及其验证证据。

系统采用 FastAPI 模块化单体。大模型负责将自然语言转换为有来源依据的结构化操作，程序负责状态更新、硬约束过滤、菜单组合、事实校验和输出。先完成 DeepSeek 等外部模型解析的完整基线，再以实际错误和时延数据决定是否加入 MacBERT、Qwen3、学习排序与路由模型。所有正式菜单使用同一套约束和校验规则。

## 1 项目目标与交付范围

### 1.1 核心目标

1. 单人推荐：根据档案、当前餐次和明确要求，给出符合已知硬约束的单餐菜单。
2. 多人推荐：建立用餐者及其约束，规划共享套餐，说明每人的适配情况及必要的分餐原则。
3. 多轮交互：支持约束追加、撤销与纠正、局部替换、整体否定、人员变化、澄清和菜单回溯。
4. 性能效率：按照官方计时方式测量首 Token、完整响应和多轮平均耗时，并记录错误与超时。
5. 可解释性：菜谱来源、约束依据、变更原因和保留内容均可追溯；支持从整餐、单菜展开到食材的营养明细。
6. 可复现性：数据、规则、模型、提示词、索引和配置具有版本记录，可以重建运行环境。

### 1.3 阶段边界

初评以有依据的定性营养评价保证基础覆盖，同时将分层营养明细纳入产品建设范围：对份量和成分数据充分的菜谱展示可追溯的定量估算，对资料不完整的项目保留缺失状态。定量功能可以在初评阶段落地，不要求先覆盖全部菜谱。系统不根据体检数值自动作出医学诊断。复杂请求仍需完成合理的任务，不能以大量无必要澄清换取表面上的低错误率。

复赛的模型部署限制、外部网络权限、硬件配置和评测协议按适用于复赛的正式要求确认，不将初评许可自动延伸到复赛。

## 3 数据基线与数据治理

### 3.1 原方案记录的数据现状

| 数据 | 原文档盘点记录 | 首次导入必须验证 |
| --- | --- | --- |
| 菜谱 | `recipes_sample_2000.csv` 共 2000 行；字段为名称、食材清单、烹饪步骤、label | 文件哈希、编码、行数、字段和解析错误 |
| 菜谱缺陷 | 1 条步骤为空、211 条 label 为空、75 组菜名重复 | 复算质量报告，逐项记录处理状态 |
| 健康档案 | 50 份详细档案，另有字段较少的简版 | 档案 ID、字段类型、单位、空值与冲突 |
| 对话 | 20 组参考用例，每组 1 至 4 轮 | 场景、人物、约束、预期行为及来源家族 |
| 第三方营养数据 | OCR 数据 1677 条、36 字段，许可范围未确认 | 授权、单位、数值错误与食材匹配；未确认前不进入正式交付 |

这些数量是继承的盘点记录，不能代替本项目实际运行的数据质量报告。导入发现差异时记录差异，不修改原始文件来迎合预期数量。

### 3.2 原始层与规范化层

原始层只读保存文件和原值。规范化层提供程序使用的字段，两层保持可追溯映射。

官方菜谱的 `recipe_id` 采用 `FT-R0001` 等系统 ID，表示映射到官方原始记录，不声称是赛方原生 ID。首次建立映射后持久化；更新数据时执行记录差异匹配，不因重新排序而重新分配全部 ID。相同菜名保留独立记录。

| 规范字段 | 用途与处理 |
| --- | --- |
| `recipe_id / dataset_version / source_record_ref` | 稳定身份、数据版本与原始记录位置 |
| `raw_name / raw_ingredients / raw_steps / raw_label` | 原始证据 |
| `canonical_ingredients` | 规范食材、别名、原文位置和映射依据 |
| `amount / unit / preparation / optional` | 份量、单位、预处理和可选性；“适量”不编造克数 |
| `categories / methods / flavor / meal_types` | 菜品类别、做法、口味和餐别，多标签表达 |
| `allergens / unresolved_ingredients` | 由审核映射计算的过敏原和未解析项 |
| `estimated_time / time_basis` | 时间及其来源、适用假设和可靠程度 |
| `source_type / review_status` | 官方或生成来源、审核状态 |
| `record_fingerprint` | 内容完整性与版本对照 |
| `nutrition_profile_ref / nutrition_revision` | 关联版本化营养明细、食材成分映射和计算依据；缺失时不补造数字 |

步骤为空的记录保留在原始数据中，默认不进入正式推荐。缺少 label 不直接删除；根据其他可靠信息补充低风险标签，高风险判断仍需审核依据。

### 3.3 食材与规则审核

建立规范食材字典、别名表、复合配料关系和过敏原映射。高风险字段由人工复核，低风险口味和类别标签可通过规则或模型辅助生成。

模型生成的映射和风险标签只作为候选，不直接成为可信事实。食材未识别不等于没有风险。对可能涉及当前过敏限制的未解析食材，排除该菜或说明信息不足。

可选辅料默认计入风险。只有规则明确允许相应调整、且输出中明确执行调整时，才能改变适用的食材集合。主食材替换、删配料、减少调味等是否保持“官方菜谱”身份，须按赛方允许的变换范围配置。

每条健康规则记录来源、适用条件、单位、强度、审核状态和版本。疾病相关信息不能机械转换为大范围禁食表；无法由现有数据可靠判定的条件应保留不确定性。

### 3.4 档案处理

以详细档案建立完整字段模型，同时接受简版及对话形成的部分档案。缺失、未知、不适用和已确认空分别表示，不通过模型自行补全健康事实。

保留原始值与规范值。BMI 复算仅作一致性检查，不静默覆盖档案值。检验值只在已审核规则适用时辅助评价，不据此新增疾病诊断。

“正式档案”指官方数据或协议约定的档案更新入口，不由对话中的自称决定。身份冲突或关键健康信息冲突时暂停相关推荐，要求澄清或通过档案入口更新。

## 4 总体架构与模块职责

### 4.1 架构选择

初评使用一个持有会话状态的 FastAPI 应用，配合 SQLite、中文关键词索引和内存向量矩阵。2000 道菜规模下，先验证轻量方案，无需预先引入独立向量数据库或微服务。

业务数据与规则不依赖具体模型供应商。模型适配器可替换，解析、规划和表达分别计时。

~~~mermaid
flowchart TD
    A["API 与会话恢复"] --> B["结构化理解与操作校验"]
    B --> C{"操作是否明确且有效"}
    C -->|否| D["保存歧义或冲突"]
    C -->|是| E["提交有效状态变更"]
    E --> F["安全候选与套餐规划"]
    F --> G["搭配评价与最终校验"]
    G --> H{"结果"}
    H -->|通过| I["事实渲染与流式发送"]
    H -->|可修复| F
    H -->|需协商或无法完成| J["具体原因与下一步"]
    D --> J
~~~

重新规划受总时限和修复次数约束。默认最终校验失败最多进行一次修复；此限制不等于候选检索只能扩大一次。所有循环都检查剩余时间。

### 4.2 业务模块

| 模块 | 职责 |
| --- | --- |
| API 适配 | 鉴权、输入协议、消息归一化、幂等、SSE 与错误映射 |
| 会话服务 | 用餐者、档案快照、餐次、有效约束、版本及请求记录 |
| 理解适配器 | 从当前状态与本轮文本生成结构化操作及证据 |
| 状态更新器 | 验证操作顺序与作用范围，以统一规则更新状态 |
| 约束引擎 | 计算有效硬约束、软偏好和共同限制 |
| 检索器 | 结构化过滤、中文关键词检索、向量召回、候选扩展 |
| 规划器 | 选择菜品、保持未受影响部分、优化搭配和偏好 |
| 生成适配器 | 在具备触发依据时补充结构化生成菜谱 |
| 营养计算器 | 根据成分记录和份量计算食材、单菜、整餐及逐人计划值，保留来源、口径和缺失状态 |
| 评价与校验 | 检查约束、来源、结构、变化范围与证据一致性 |
| 输出渲染器 | 用校验后的事实生成菜单、理由和调整说明 |
| 评测与观测 | 白盒检查、黑盒对话、模型实验、时延与故障记录 |

### 4.3 在线理解路线

第一阶段统一采用外部大模型结构化解析，建立完整基线。后续再加入快速理解通道。

| 路线 | 进入条件 | 行为 |
| --- | --- | --- |
| 快速理解 | 已验证规则或本地模型能够可靠理解操作、人物和范围 | 不调用外部模型，进入共同规划与校验流程 |
| 增强理解 | 本地解析不可靠，但现有信息原则上足够解释 | 由外部模型复核，输出同一操作契约 |
| 澄清 | 用户信息本身缺失、指代有歧义或要求需协商 | 提出能消除具体不确定性的一个问题 |
| 依赖故障 | 必需解析服务不可用，且本地无法可靠处理 | 返回明确的暂不可用说明，不冒充用户表达不清 |

人数多或组合计算困难，不自动触发大模型升级。语义已经明确时，由规划器处理计算难度。模型更强也不能补出用户尚未提供的事实。

## 5 核心对象与状态契约

### 5.1 身份与版本

| 对象 | 核心字段 | 语义 |
| --- | --- | --- |
| Conversation | `session_id, principal_id, state_revision` | 会话隔离及权威状态版本 |
| Diner | `diner_id, aliases, attendance, profile_version` | 稳定人物身份、称谓及本餐是否参加 |
| Meal | `meal_id, meal_type, active_diners, status` | 同一餐的任务范围，独立于菜单版本 |
| Constraint | `constraint_id, subject, scope, severity, status` | 谁受约束、持续多久、是否可协商 |
| PlanVersion | `plan_id, parent_plan_id, restored_from, based_on_state_revision` | 菜单谱系、恢复来源与生成依据 |
| RequestRecord | `request_id, idempotency_key, request_hash, processing_status` | 重试、追踪与恢复 |
| PendingIssue | `issue_id, alternatives, affected_scope, safety_hold` | 尚未解决的歧义与暂停推荐范围 |

`meal_id` 在同一餐的换菜与回滚中保持不变。`plan_id` 每次形成新菜单时变化。开始新餐时，餐次级约束到期，会话级及档案级约束按规则继续有效。

### 5.2 约束结构

每条约束至少包含：

- 类型与值：过敏、明确禁食、食材排除、口味、菜数、结构、时间等。
- 人物与范围：指定 `diner_id` 或全桌；档案长期、会话或本餐。
- 来源：档案版本、本轮原文证据、历史轮次或审核规则。
- 强度：硬约束、软偏好或可协商默认值。
- 生命周期：`active / revoked / superseded / pending`。
- 变更依据：新增、撤销或纠正该约束的事件 ID。
- 可信信息：审核依据与解析置信度分别保存，不能混为一个分数。

用户明确指定“只能三道菜”“不要某种食材”时，根据表达语义建立硬要求；“最好”“尽量”等建立软偏好。默认搭配不能悄悄覆盖明确要求。

### 5.3 菜单状态分为三个维度

| 维度 | 状态 | 作用 |
| --- | --- | --- |
| 校验状态 | `unvalidated / valid / stale / invalid` | 是否在指定约束和数据版本下可使用 |
| 发送状态 | `pending / streaming / completed / interrupted` | 是否完成服务端发送 |
| 用户态度 | `unconfirmed / confirmed / rejected` | 用户是否明确认可或否定 |

`completed` 不代表用户确认，也不保证客户端已经阅读。已有菜单在状态变化后可以成为 `stale`；即使历史发送成功，也必须重新校验后才能作为当前建议。

### 5.4 菜单记录内容

保存菜品槽位、菜谱快照、官方或生成来源、可用人员、定性适配、已满足约束、未满足软偏好、变更集合和校验依据。提供定量明细时，同时保存计划份量、分配依据及版本化营养快照。记录当时的数据、规则、模型、配置版本。

官方同名菜通过 ID 和食材、步骤区分。生成菜通过会话内唯一 ID 和不可变内容快照区分，不只保存显示菜名。

## 6 结构化理解与复合操作

### 6.1 理解输入

模型读取本轮新增文本、稳定人物表、当前餐次、有效约束、当前展示菜单及必要的历史摘要。不能仅凭本轮单句完成所有跨轮指代。

原始历史用于审计、证据定位和必要的重新解析，日常业务决策读取结构化状态。历史摘要不能替代保存的硬约束。

### 6.2 操作集合

支持 `START_MEAL`、`ADD_DINER`、`REMOVE_DINER`、`ADD_CONSTRAINT`、`REVOKE_CONSTRAINT`、`CORRECT_FACT`、`UPDATE_PREFERENCE`、`REPLACE_DISH`、`ADD_DISH`、`REMOVE_DISH`、`REJECT_PLAN`、`RESTORE_PLAN`、`CONFIRM_PLAN`、`ANSWER_CLARIFICATION` 和 `ASK_INFO`。

操作不直接操作数据库。状态更新器根据当前版本、权限、作用范围和业务前置条件执行。

### 6.3 结构化示例

以下为“这顿不要鱼，把第二道菜换掉，其他不变”的内部解析示例。置信度数值仅演示字段，不代表已实测。

~~~json
{
  "schema_version": "nlu.v2",
  "base_state_revision": 7,
  "meal_id": "M001",
  "operations": [
    {
      "type": "ADD_CONSTRAINT",
      "subject": "table",
      "scope": "meal",
      "payload": {
        "constraint_type": "excluded_food",
        "normalized_value": "fish",
        "severity": "hard"
      },
      "evidence": {
        "message_id": "MSG008",
        "text": "这顿不要鱼"
      },
      "confidence": 0.98
    },
    {
      "type": "REPLACE_DISH",
      "subject": "table",
      "scope": "meal",
      "payload": {
        "slot_id": "slot_2",
        "preserve_other_slots": true
      },
      "evidence": {
        "message_id": "MSG008",
        "text": "把第二道菜换掉，其他不变"
      },
      "confidence": 0.96
    }
  ],
  "unresolved": [],
  "model_version": "parser-candidate"
}
~~~

先新增约束，再据此替换。如果其他菜也包含鱼，安全限制优先，系统可以进一步替换受影响菜并解释原因；“其他不变”不能使已冲突菜继续进入正式菜单。

### 6.4 操作验证

验证 Schema、对象存在性、人物归属、证据、作用范围、生命周期和操作前置条件。JSON 合法只证明格式，不能证明理解正确。

同一轮的关联操作作为一个明确的状态变更批次处理。批次存在关键歧义时，不提交猜测结果，保存待澄清记录。若出现尚未确定的新安全信息，将相关当前菜单标为暂不可直接复用，直到澄清完成。

新增要求与不可移除的安全限制发生直接矛盾时，将该要求记录为待协商意图，不通过覆盖已有安全事实使它成为可执行状态。只有待协商事项得到明确解决后，才应用对应操作。

普通对话不能直接删除正式档案的过敏或禁食。用户纠正“过敏的是妹妹，不是我”时，需要区分人物归属纠正与移除真实安全限制；有冲突则澄清，正式档案变更走约定入口。

人物不参加本餐时，移除其对本餐聚合约束的贡献，保留其个人档案和历史事实。

### 6.5 状态提交与发送解耦

一个明确且验证通过的操作批次，先以短事务提交为新的 `state_revision`，再据此规划菜单。提交和请求记录更新保持原子性。

规划失败或回答断线，不自动撤销已经正确接收的用户要求。旧菜单按新状态重新判断有效性；不能因为它是上一份完整回答就继续当作安全结果。

## 7 多轮修改 回溯与冲突处理

### 7.1 最小修改

每次修改先建立影响集合，包含直接目标槽位、命中新约束的菜品，以及结构变化导致的关联项。对仍然有效的其他菜品优先保留。

先在受影响槽位中搜索；无可行组合时逐步解锁相关槽位。不得因局部搜索失败直接推翻整桌。用户明确要求“全部重做”时允许全量重规划，但保留有效的健康与餐次约束。

在必须满足的约束内，依次比较修改菜品数量、其他方案变化、搭配质量、偏好和时间等指标。采用字典序或分阶段优化实现这一优先关系，避免任意权重抵消保留要求。

每次保存 `change_set`，列明原菜、新菜、触发约束和额外修改原因。启发式方法报告实际修改数量；未证明最小性时，不声称获得全局最少修改。

### 7.2 版本恢复

“上一版”默认指当前展示菜单的上一个历史展示版本，不是查询最近一个 `completed` 记录。显式版本名称或 ID 优先；目标不明确时澄清。

恢复历史菜品内容时，保留当前有效的档案、参与人员及本餐约束。历史菜单重新校验后生成一个新版本，保存 `restored_from`；不修改历史记录。需要继续向前回溯时沿保存的历史游标定位，避免在恢复产生的新版本间反复跳转。

例如当前 V2、上一版 V1：恢复 V1 后产生 V3。V3 的恢复来源为 V1，生成依据为当前状态；V1 当时使用的健康约束不能覆盖当前健康事实。

### 7.3 否定与澄清

“换掉第二道菜”按局部否定处理；“整桌都不要”按菜单级否定处理。没有证据时，不能将否定某道菜扩大为永久排斥其所有食材。

用待澄清问题 ID 关联后续回答。“那个”“都行”“按刚才的”结合当前待解决事项解析，不能默认解释成取消全部限制。

每次优先提出一个最能解决当前不确定性的问题。口味的低风险模糊表达可以使用已声明默认值；涉及人物、过敏、禁食或无法完成结构要求时才追问必要内容。

### 7.4 结果类型

| 内部结果 | 含义 | 用户可见行为 |
| --- | --- | --- |
| `PLAN_READY` | 存在通过校验的方案 | 展示菜单和必要解释 |
| `CLARIFICATION_REQUIRED` | 用户可以补充的关键信息尚不明确 | 提出具体问题 |
| `CONSTRAINT_CONFLICT` | 已知要求无法同时满足 | 说明冲突，协商可调整要求 |
| `CATALOG_INFEASIBLE` | 在明确覆盖范围内证明官方库无法满足 | 按生成策略处理或解释限制 |
| `SEARCH_INCOMPLETE` | 候选覆盖或搜索尚不充分 | 在预算内扩大搜索，不声称无解 |
| `TIME_BUDGET_EXHAUSTED` | 总时间预算不足 | 有可行结果则返回；否则明确说明未完成 |
| `DEPENDENCY_UNAVAILABLE` | 必需服务不可用 | 受控降级或明确暂不可用 |
| `DATA_CONFLICT` | 档案身份或关键数据矛盾 | 按协议报错或要求确认 |

不能将所有失败归类为“用户需求不清楚”。只有用户能解决的不确定性才进入澄清。

## 8 约束引擎与多人适配

### 8.1 硬约束先于排序

先构造可行候选，再优化偏好。过敏、禁食、来源边界及其他明确硬要求不能被相似度、口味或多样性得分抵消。

约束采用来源、作用范围和生命周期处理，不简单地“新消息覆盖全部旧要求”。正式档案安全限制持续有效；当前轮可改变旧软偏好；系统默认在与明确要求冲突时让位。

### 8.2 共享菜单默认策略

初评默认采用共享菜模式：任一参加本餐的用餐者的已知过敏和明确禁食，聚合为全桌限制。保留每条限制的原人物来源，人员变化时重新计算。

软偏好尽量兼顾每个人。优先选多样化基础菜；独立蘸料、差异菜等只在其来源、食材和使用范围可以明确校验且不改变安全承诺时采用。不要以“过敏者不吃这道”绕过当前共享菜规则。

每份菜单按人物检查硬约束及适配情况，输出简短说明。缺少完整档案时，仅对已知条件给出适配判断，不能宣称全面健康适合。

### 8.3 规则数据与计划结构

蛋白质来源、蔬菜、主食、汤、凉菜等作为可重叠的菜品属性。混合菜可以覆盖多个角色，不能为同一道菜虚构多份食物。

原方案人数与菜数可保留为可调整的初始默认：1 人 1 至 2 道，2 人 2 至 3 道，3 至 4 人 3 道加汤，5 至 6 人 4 道加汤。它们是工程默认，不是营养标准。显示菜数是否包含汤、主食必须一致；用户明确指定数量时按其语义执行。

完整单餐规划、仅推荐一道菜和局部增删，分别适用不同结构检查，不强行把每次操作变成完整宴席。

## 9 检索与候选覆盖

### 9.1 检索流程

1. 根据有效状态生成结构化查询。
2. 使用审核规则对完整官方目录做硬约束预过滤。
3. 在安全集合中执行中文关键词和向量召回。
4. 按 ID 合并、去重，保留类别覆盖和检索理由。
5. 使用可解释规则排序建立基线，需要时再加入学习排序。
6. 对候选执行同一硬约束断言，再交给规划器。
7. 未找到方案时扩大候选范围，并记录覆盖程度。

禁止先让模型自由编菜名，再通过模糊匹配找一个近似官方记录作为来源。

### 9.2 中文索引

FTS5 不默认等同于中文分词。导入时为菜名、食材和做法构造分词字段；入库与查询使用一致的词典和分词版本。

规范食材和过敏关系使用结构化索引，处理“番茄／西红柿”等别名。针对“鱼、蛋、奶”和两字食材建立精确查询或短词回退，不能只依赖 trigram 的全文匹配。

词法召回和向量召回保留独立分数。基线可采用按排名融合的方法，或经验证的分数归一化后组合，避免把不同尺度的原始分数直接相加。

### 9.3 候选扩展与无解判断

每个检索结果附带 `search_coverage`，至少区分 Top-K 候选、扩展候选和完整安全目录。分类候选为空时先检查映射、标签和召回是否漏项。

只有在明确覆盖范围内完成有效判定，才报告该范围无可行菜谱。Beam 搜索没找到套餐、某次 Top-K 为空和全库无解分别记录。

检索评测包括别名与短词召回、类别覆盖、候选集可组成套餐的比例，以及扩大候选后的收益；不能只看单道菜相关性。

## 10 套餐规划与分层营养分析

### 10.1 第一版规划器

基线采用分类型候选池和限时 Beam Search，优先保证简单、可调试和完整任务完成。搜索保存已验证的可行候选，时间不足时可返回已验证的当前最佳可行结果。

每次扩展检查能够提前判断的硬约束，避免把明显不可能的部分套餐留到最终校验。搜索宽度、候选数量和各阶段预算集中配置，以回归结果选择。

小规模实例使用枚举或精确求解作参考。后续若组合质量、最小修改或冲突诊断成为瓶颈，可比较 MILP／CP-SAT；不要求初版同时维护多种求解器。使用 CP-SAT 时需正确处理整数化与舍入，不能把近似后的模型结论冒充原问题结论。

### 10.2 排序与套餐评分分工

| 环节 | 可使用的信息 | 不应混淆的内容 |
| --- | --- | --- |
| 候选排序 | 用户要求、单菜属性、词法和向量匹配、时间可靠度 | 尚未形成的部分套餐不能被当作已知输入 |
| 套餐扩展评价 | 当前已选菜、候选的增量贡献、重复度与类别覆盖 | 单菜相关性标签不能直接替代组合质量标签 |
| 完整菜单评价 | 整体结构、逐人适配、软偏好、修改范围 | 总体得分不能覆盖某位用餐者的硬违规 |

初版使用可解释的套餐评价函数。若训练带套餐上下文的排序器，数据中必须包含对应部分套餐和候选条件。

### 10.3 初评营养评价

| 维度 | 评价方式 |
| --- | --- |
| 食物结构 | 检查适用任务下是否具有合理的食物类别组合 |
| 蛋白质与蔬菜 | 依据实际食材识别来源，避免只按菜名猜测 |
| 烹饪多样性 | 评价重复做法，结合审核规则处理高风险场景 |
| 油盐糖 | 保留“适量”等不确定性；不给出伪精确数值 |
| 多人适配 | 对每人已知条件逐项核对，记录未满足软偏好 |
| 份量 | 给出有依据的建议份量或分餐原则，估算明确标注 |
| 时间 | 区分步骤给定时间与估算，写明必要的器具或并行假设 |

对严格数量上限，缺少数量数据时不能仅凭“清淡”标签判定通过。可在明确允许的调整范围内提出可执行做法；无法可靠判断时说明限制或选择依据更充分的菜。

定量营养明细按 10.4 节建设，统一食材可食部、生熟重量、份量、成分来源和误差口径。逐人计划摄入按分配份量计算，不能将全桌总量简单除以人数。先上线数据充分的覆盖范围，未覆盖项继续提供有依据的定性分析。

### 10.4 借鉴 ZOE 的分层营养明细

本功能已纳入产品方案。用户可以先看整餐结论，再逐层查看单菜和食材的糖、蛋白质、碳水化合物等明细，理解营养构成及局部修改的影响。界面展示与 API 回答共享同一份经校验的数据。

#### 10.4.1 展示层级与交互

| 层级 | 展示内容 | 用户操作 |
| --- | --- | --- |
| 整餐概览 | 简短搭配说明、主要营养估算、数据覆盖情况；明确整桌或指定用餐者口径 | 展开单菜贡献，切换用餐者 |
| 单菜分析 | 每份或整道菜的营养量、份量、生熟口径、主要贡献食材 | 查看食材、修改计划份量、比较替换方案 |
| 食材明细 | 每项食材的用量及各项营养贡献，包含已计入的辅料和调味料 | 查看成分来源、映射说明和计算依据 |
| 修改对比 | 原方案与候选方案的营养变化、受影响菜品和保留内容 | 接受或取消建议，查看修改原因 |

默认显示摘要，详细表格按需展开。所有层级都标注统计范围，避免把整道菜、每份和某人的计划摄入混为一谈。计划数据不表述成实际摄入记录。

可视化优先使用数值表格和单项营养素的贡献条形图，例如各道菜对本餐蛋白质的贡献；数据不完整时标明已知部分。不要把总糖、膳食纤维和总碳水作为互不重叠的类别画成同一个占比饼图。

#### 10.4.2 首批营养字段及口径

| 字段 | 单位 | 展示与计算规则 |
| --- | --- | --- |
| 能量 | kcal | 保留成分来源所采用的能量计算方法，避免跨口径简单替换 |
| 蛋白质 | g | 展示份量对应含量；可展开各食材贡献 |
| 脂肪 | g | 与蛋白质、碳水分列；数据充分时再展开脂肪类别 |
| 碳水化合物 | g | 保存原始字段定义，注明是否包含膳食纤维 |
| 总糖 | g | 与碳水化合物区分；不能用烹饪时加入的白糖量代表整道菜总糖 |
| 添加糖 | g | 有可追溯配方或标注数据时单列；属于总糖的组成部分，不与总糖重复相加 |
| 膳食纤维 | g | 独立保存其数值、定义和来源；缺失时不能当作零参与净碳水计算 |
| 净碳水估算 | g | 显示所采用的派生方法和适用范围，提供展开查看公式的入口 |
| 钠 | mg | 数据和用量充分时展示，调味品数量未知时保留缺失状态 |

糖字段明确区分总糖和添加糖。FDA 对两者关系的说明可用于核对数据语义，但不将其人群参考值直接套用为本项目的个人目标。

净碳水作为需要明确方法的派生字段处理。第一版可支持一种受限口径：来源字段明确包含纤维的总碳水，减去同一基准下的膳食纤维，展示为“净碳水估算（总碳水－膳食纤维口径）”。含糖醇或其他需单独处理成分的记录，待方法明确后再支持；如果来源已经提供扣除纤维的碳水字段，不再次扣减。不把糖从碳水中扣除，也不把净碳水数值直接转换成个人血糖反应结论。USDA Foundation Foods 的 carbohydrate by difference 包含膳食纤维，可作为核对来源语义的一个例子。

#### 10.4.3 数据建设与计算

优先使用赛方实际提供、定义完整且可追溯的营养字段；缺失部分可引入许可适用的食物成分数据。记录数据库名称、版本、记录 ID、食材名称、品牌或品种、生熟状态、每 100 g 等基准、单位和计算方法。外部数据对本地食材的映射需要复核，不仅凭名称相似度选第一条。

在重量与成分数据的状态一致时，单项食材某营养素的基础换算为：本次用量贡献 = 可食部分重量 ÷ 100 × 每 100 g 成分含量。随后按当前配方聚合为单菜，再按实际计划分配聚合为个人和整餐。烹调后数据、原料投入估算以及采用出成率或保留率的估算分别标注方法，避免重复校正或将原料合计声称为实测成品含量。

每个营养值至少关联数值、单位、统计基准、来源记录、计算方法和完整性状态；份量另行记录来自原配方、用户输入还是明确标注的估算。完整性与方法分开表达：数据完整仍可能只是计算估算，不代表实测结果。

缺失按营养素分别传播。例如某调味料只有钠数据，不能推断其总糖为零。部分食材数据缺失时，可显示“已知食材小计”和缺失项，但不能将小计标作整餐总量，或据此判定数量上限已满足。不使用模型生成貌似精确的缺失数值，也不凭空给出误差区间。

多人分配同时约束份量的一致性，个人分配不能超出该菜实际计划量。均分仅在明确采用均分假设时使用并显示该假设；不等份或存在挑选食材时，分别保存分配依据。后续用户修改份量或食材，会产生新的菜单版本，并触发营养重算和必要的约束校验。

#### 10.4.4 与局部替换及性能的衔接

“换一道”可以同时展示菜品变更和营养差异。对比采用同一统计范围、可比较的份量与数据方法，明确说明份量是否一起变化；某项数据不完整时不输出该项确定的增减值。硬约束校验独立执行，营养改善不能抵消过敏或禁食冲突。

成分映射和基础营养尽量离线处理，在线使用程序完成份量换算与汇总。前端展开明细直接读取当前菜单的营养快照，不为每一层展开额外调用大模型。缓存关联菜谱快照、份量、生熟与计算方法、成分数据库版本；逐人结果另关联人员分配，防止沿用旧数值。

数据充分时，API 可以在用户追问“糖主要来自哪道菜”“换掉后蛋白质变化多少”时给出同源解释。首屏不强制输出完整营养表，正式流式协议和已有时延要求保持兼容。

#### 10.4.5 实施与验收

首批选择团队拟用于完整演示且数据充分的菜谱建立明细，公开实际覆盖数量和未覆盖原因，不宣称全部 2000 道均已支持。扩展到更多菜谱以数据质量为依据。

验收应覆盖：独立计算可复算；相同方法下份量变化与营养变化一致；整餐汇总和食材贡献一致；逐人分配不超量；总糖与添加糖不重复计数；不同碳水定义不会重复减纤维；缺失字段不变成零；替换、恢复版本后不会显示旧营养值。显示精度与来源相匹配，舍入后的细项和总计差异应可解释。

这项能力作为营养解释与交互的正式增强项，在业务基线跑通后推进。全量营养数据补齐不阻塞可交付系统，已上线的明细则必须满足上述验收要求。

## 11 受控生成菜谱

### 11.1 生成触发

官方库始终优先。按以下内部原因记录生成决策：

| 原因 | 处理 |
| --- | --- |
| `CATEGORY_EMPTY` | 完整安全目录中某必需类别无可用记录，允许按配置进入生成 |
| `COMBINATION_INFEASIBLE` | 类别均有候选，但有可靠证据表明官方组合无法满足，允许按配置进入生成 |
| `SEARCH_INCOMPLETE` | 召回或搜索覆盖不足，先扩大搜索，不以此触发无解生成 |
| `SEARCH_TIMEOUT` | 未完成求解，不等于库内无解；优先返回已有可行结果或明确未完成 |
| `PREFERENCE_ONLY` | 仅因分数较低、不够新颖或想展示生成能力，不触发 |

初版先实现容易验证的 `CATEGORY_EMPTY`。组合无解分支在具备可靠诊断后启用，不强行引入无法验证的证明机制。

无解证据说明采用的约束、候选覆盖和判定方法。超出适用范围的“无解”结论不得使用。

未解析食材、缺失类别或未审核数据导致候选不可用时，记录数据不足原因。此时可以说明“当前审核数据中没有能够确认可用的候选”，不能扩大为对完整菜谱事实的无解证明；是否进入生成按已确认的生成策略处理。

### 11.2 生成与编译校验

生成器输入有效约束、允许食材词表、所需菜品角色和输出 Schema，输出食材、可识别份量、步骤、做法及时间依据。

程序独立执行：

1. 将所有食材和调料映射到审核词表。
2. 从可信映射重新计算过敏原与禁食命中。
3. 核对步骤中使用的食材是否全部列入食材表。
4. 核对输出理由是否增加未批准配料或份量要求。
5. 检查多人约束、菜品结构及当前任务要求。
6. 对超出规则能够判断的内容保留不确定性，必要时放弃生成项。

模型提供的风险标签不作为自我证明。初版生成优先使用已审核的食材和烹饪方式；无法可靠识别的配料不进入正式菜单。时间估算和烹饪可执行性也需要证据边界，不能将模型自报时间当作已验证事实。

### 11.3 来源与保存

生成菜使用会话内唯一 `GEN-` ID，保存不可变内容快照、生成依据及校验记录。正式文本明确标注“智能生成”，不冒充官方库记录。

生成菜不执行官方记录存在性断言，但必须执行生成记录存在性、会话归属、内容完整性和安全断言。未经独立审核，不回写正式官方目录。

## 12 最终校验与回答

### 12.1 最终校验输入

使用当前状态版本、可信档案、审核规则、菜谱快照和规划结果校验。不得只检查解析模型自行提供的风险结论。

最终校验至少覆盖：

- 参与人员、约束主体与当前餐次是否正确。
- 过敏、禁食及其他硬要求是否满足。
- 官方记录是否真实对应，生成记录是否正确标注。
- 实际食材、辅料、步骤与所使用的风险映射是否一致。
- 菜数、任务结构及明确指定的要求是否满足。
- 局部修改是否发生非必要扩张，是否保留变更理由。
- 是否遗漏已明确的约束、是否把未知信息当成确定事实。
- 输出事实是否与菜单和当前状态一致。

通过后保存校验结果及版本引用。任何改变菜品、食材或份量的后续步骤都必须重新校验。

### 12.2 共用事实输出层

两条理解通道共用事实渲染器。菜单名称、ID、来源、人员、约束、份量和变更均从已验证字段生成。

初版采用可组合模板表达。推荐理由由明确的理由代码和事实依据生成，例如“保留三道未受影响菜品”“替换命中新禁忌的汤”。模板可具备多种自然表述，但不能改变事实。

大模型可参与复杂理解、冲突分析和澄清内容选择。后续如果试验自由润色，必须在发送前检查其全部新增事实；无法可靠核验时使用模板。不能先发送任意自由建议，再等待后置校验发现错误。

### 12.3 回答结构

通常按以下顺序输出，根据当前任务压缩无关部分：

1. 菜单或明确业务结论。
2. 菜谱来源和必要的 ID。
3. 与当前健康限制、偏好相关的简要理由。
4. 定性搭配及必要的分餐说明；数据充分或用户追问时展开营养明细，标明份量和估算口径。
5. 本轮改动、保留内容及原因。
6. 需要用户决定的一个具体问题，仅在必要时出现。

一般咨询不必重复整个菜单。解释不输出医学诊断，不夸大适配范围，也不把未计算的营养量写成确定数值。


## 13 API 会话协议与幂等

### 13.1 对外接口

| 路径 | 用途 |
| --- | --- |
| `POST /v1/chat/completions` | 正式文本对话接口，支持流式与非流式 |
| `GET /health` | 进程存活检查 |
| `GET /ready` | 本地必需数据、配置和运行组件就绪检查 |
| `/docs` | 联调接口说明 |
| `/internal/*` | 结构化调试和评测辅助，使用独立管理员权限 |

兼容范围先限定为评测需要的文本请求和文本回答，不承诺实现完整 OpenAI 产品功能。扩展上下文字段通过适配层处理，最终以赛方联调协议为准。

### 13.2 请求示例

~~~json
{
  "model": "fangtai-meal-agent",
  "messages": [
    {
      "role": "user",
      "content": "这顿不要鱼，把第二道菜换掉，其他不变"
    }
  ],
  "stream": true,
  "user": "U001",
  "context": {
    "session_id": "S001",
    "user_id": "U001",
    "meal_id": "M001",
    "client_turn_id": "T008",
    "base_state_revision": 7
  }
}
~~~

`client_turn_id` 和 `base_state_revision` 为可选工程扩展，不要求赛方必须传入。未传版本时，服务端依靠会话锁和内部版本管理保证一致性。

会话 ID 可以兼容 `context.session_id`、`X-Session-ID` 和顶层 `session_id`，但多个入口同时出现且值不同，应报告冲突，不通过优先级掩盖错误。用户 ID 不能直接代替会话 ID。

缺少会话 ID 的首轮请求可以创建新会话，通过约定响应头返回 ID。后续省略历史的请求必须带可识别会话；不能猜测该用户“最近的一次会话”。完整历史模式的会话恢复方式在联调时明确。

### 13.3 两种消息输入模式

**增量模式：**请求仅包含本轮新增消息，服务端读取已保存状态。

**历史模式：**请求包含完整历史，服务端先与已记录的历史前缀对齐，只处理新的后缀。首轮导入历史时按约定重建状态，并记录哪些轮次已应用。

历史不一致、客户端删改关键已处理消息或人物事实时，不悄悄重新执行全部消息。返回冲突信息或进入明确的历史修正流程。优先使用消息 ID、轮次 ID 和内容摘要对齐；没有这些字段时采用经过验证的历史前缀匹配。

相同文字可以是两次合法请求，不能用文本相等作为唯一去重规则。已处理的“加一道汤”也不能因完整历史再次出现而被重复执行。

### 13.4 幂等与重试

幂等键按调用身份和会话隔离，绑定规范化请求哈希。

| 情况 | 行为 |
| --- | --- |
| 同键同请求仍在处理 | 返回处理中状态或约定的短等待，不再执行状态操作 |
| 同键同请求已完成，状态尚适合重放 | 返回保存的结果，不重复增菜或改约束 |
| 同键不同请求内容 | 返回 409，避免错误复用 |
| 发送中断且无后续轮次改变状态 | 可重放该轮已验证响应，不重新应用操作 |
| 旧键重试时会话已推进，原结果已不适合当前状态 | 返回过期重放冲突，不将旧菜单作为当前建议发送 |

幂等首先保证业务变更只执行一次。重放还要检查状态有效性，不能为了逐字返回旧答案而忽略之后新增的安全约束。

### 13.5 SSE 与提交时机

首个有效菜单内容只能在最终校验后发送。发送前已保存的用户状态不会因断线丢失。发送完成后，以短事务记录 `completed` 并更新当前展示菜单；中断则标记 `interrupted`。

已经提交新约束但旧展示菜单仍存在时，旧菜单标为 `stale`；下一轮可将它作为修改起点，但必须重新校验。这个过程不将“上一份完整菜单”误认为“仍满足当前约束的菜单”。

正式响应使用约定的 Chat Completions 文本结构与 SSE 结束方式。非流式接口返回等价最终内容。内部结构化调试结果不混入正式评测响应。

SSE 头一旦发送，不能再通过更改 HTTP 状态处理后续异常。因此尽量在开始发送前完成必需依赖调用、规划和校验；发送期主要负责输出已经确定的文本。

### 13.6 错误语义

| 场景 | HTTP 或流式行为 |
| --- | --- |
| 正常菜单、必要澄清、业务约束冲突 | 200，给出明确文本结果 |
| 鉴权缺失或无权访问 | 401 或 403 |
| 请求无法解析、必要字段不符合约定 | 400 或 422 |
| 身份冲突、历史冲突、版本冲突、幂等内容冲突 | 409 |
| 同一会话超过短等待仍繁忙 | 409，错误类型为 `SESSION_BUSY` |
| 全局容量已满 | 429，可提供重试提示 |
| 必需依赖不可用且无法完成请求 | 发送前返回 503 |
| 流式连接中断 | 记录中断，保留状态和请求记录，不假报完整成功 |

一次请求是否算成功，应根据业务结果判断，不能只看 HTTP 200。

## 14 存储 并发与缓存

### 14.1 单体与计算执行

初评由单个 API 进程管理会话权威状态和会话锁。不同会话可以并发；同一会话的状态操作及当前回答按顺序处理，使用有界等待。

外部调用采用异步 I/O。较重的本地推理、搜索与同步访问根据实际耗时进入受控执行池，避免阻塞事件循环。计算工作单元接收不可变输入快照，不独立修改会话；结果返回主流程后检查状态版本再提交。

计算工作进程与多个独立 API 实例是两种部署方式。只有后者需要解决跨实例会话锁、共享状态和一致性问题，不因使用计算工作池就立即引入分布式组件。

### 14.2 数据库事务

数据库事务保持短小，不包围外部 API 调用或整个流式发送。请求记录、状态变更和版本递增在对应短事务中一起写入。

规划失败、依赖错误和断线的结果均写入请求记录。重启后可以判断请求处于解析、状态已提交、菜单已生成或发送未完成的哪个阶段，防止重复执行操作。

### 14.3 资源保护

使用全局并发信号量、有限队列和分模块预算。容量不足时及时返回容量结果，不能让排队请求无限累积。

同会话锁可以覆盖一个有界轮次，但不等于持有数据库写事务。超时或断开后在清理路径释放锁，保留必要状态记录。

### 14.4 缓存边界

- 共享缓存保存公开菜谱、规范词典、向量、规则及不含个人信息的索引结果。
- 使用个人约束形成的检索结果及最终回答按身份、会话和有效状态隔离。
- 缓存键包含适用的数据、规则、档案、餐次、约束及模型或配置版本。
- 新增禁忌、人物变化或规则更新后，旧缓存必须失效或重新验证。
- 在菜单回溯中引用历史快照，不将缓存命中视为新的安全证明。

会话有效期和数据保留策略配置化。正式多轮评测窗口内，不能因过短过期时间丢失上下文。

## 15 模型实验与发布策略

### 15.1 保留候选 收缩强制训练范围

| 候选 | 适合解决的问题 | 启动条件 |
| --- | --- | --- |
| DeepSeek 等外部大模型 | 完整语义理解基线、复杂操作复核 | 首先接通，用于形成业务与时延基准 |
| 规则或传统分类器 | 明确、重复、高频的简单操作 | 已有可定义的任务边界和错误样本 |
| MacBERT 多任务模型 | 意图、实体与范围等结构化预测 | 有足够审核标签，并明确输入包含必要上下文 |
| Qwen3 小型模型 | 结构化操作序列与 JSON 生成 | 同一输出契约下存在值得比较的质量或速度收益 |
| LightGBM Ranker | 安全候选内的条件化偏好排序 | 有真实的查询条件与相关性或成对偏好标签 |
| 学习式路由器 | 预测本地解析能否可靠直出、升级是否有益 | 已有独立样本上的错误与升级收益记录 |

Qwen3 0.6B 可以保留为候选，不预设它必然满足跨轮理解。MacBERT 和 Qwen3 不构成必须先后完成的训练依赖；它们共同依赖任务契约、数据和评测口径。

固定菜谱的类别标签可先离线整理。若没有可证实的额外收益，不为固定数据专门增加在线分类器。

### 15.2 三组系统对照

| 组别 | 组成 | 目的 |
| --- | --- | --- |
| A 完整基线 | 外部模型解析，共同状态机、规划器、校验器与模板输出 | 建立业务质量与速度基准，优先可交付 |
| B 轻量理解 | 规则或传统模型处理已覆盖操作，其余回到 A 的解析能力 | 测量简单请求加速及误放行风险 |
| C 小模型理解 | MacBERT 或小型生成模型的独立子变体，加可靠回退 | 比较质量、覆盖率、时延和维护成本 |

三组均使用相同的菜谱数据、约束语义、规划与输出规则。比较解析器时不同时更换排序器；比较排序器时不同时更换解析器。联合系统实验用于比较最终组合，单模块消融用于解释收益来源。

### 15.3 训练与校准数据

先定义正确的状态变化，再撰写或生成不同表达方式。样本保存初始状态、本轮文本、正确操作、下一状态及必要的菜单行为。高风险事实由人工复核。

训练、验证和独立测试按完整场景、来源模板和改写家族分组。相同原始场景的所有变体位于同一分区。官方菜谱本身可作为检索数据共享，但测试问法、预期标签及答案不能用于模型选择。

训练集用于拟合；验证集用于选择模型、阈值、提示词、供应商和配置；冻结方案后使用独立测试集报告结果。不要把“真实测试集”作为持续调参集。

路由器使用未参与底层模型相应拟合的样本预测记录，可采用单独留出集或交叉验证方式产生记录。避免用训练内预测的高置信度学习路由。

### 15.4 评测指标

解析器除了意图和实体指标，还必须报告人物与范围准确性、复合操作正确率、完整下一状态正确率及高风险遗漏。

路由器报告快速通道覆盖率、错误放行率、不必要升级率、必要澄清识别情况和升级收益。置信度需在验证集上校准，不能直接相信模型自报分数。

发布依据端到端任务质量和耗时。离线指标较高但增加安全错误或使多轮耗时恶化的模型，不进入正式组合。

## 16 性能目标与测量

### 16.1 官方要求与内部目标

| 指标 | 题面优秀档 | 题面合格档 | 内部报告 |
| --- | --- | --- | --- |
| 首 Token | 小于 2 秒 | 小于 5 秒 | 均值、P50、P95、P99、超时率 |
| 单轮端到端 | 小于 8 秒 | 小于 15 秒 | 按场景与通道分组统计 |
| 多轮平均 | 小于 6 秒 | 小于 12 秒 | 按完整场景及整体汇总报告 |
| 并发 | 补充口径称支持可加分 | 如实说明能力 | 可先以 10 个独立会话作压测目标，结果决定声明值 |

内部可将 P95 对齐优秀档作为工程目标，但这不是赛方已宣布的百分位判分规则。P95 达标也不能隐藏尾部失败。所有数字均为目标，不代表当前方案已经达到。

### 16.2 计时点

记录客户端发出请求、服务端接收、进入队列、解析完成、状态提交、检索完成、规划完成、最终校验、首个非空有效 content、最后一个内容分块和流结束的时间。

正式性能结论按赛方测试客户端口径计算；内部同时保留网络、排队和业务阶段耗时。角色字段、空块和心跳单独记录，不用于替代有效回答时延。

模型服务自身 TTFT 不能代替业务 API 的 TTFT。模板输出也需要计入此前的理解、检索、规划和校验时间。

### 16.3 全局时间预算

一个请求只有一个总截止时间，包含排队、外部调用、重试、搜索、生成、校验和输出准备。每个模块读取剩余预算，循环搜索内部也检查。

外部调用最多进行有限重试，且必须满足剩余预算。已完成理解而仅表达服务故障时直接使用模板；理解本身未完成且本地无法可靠处理时，返回依赖故障或必要澄清，不输出未经理解验证的菜单。

生成菜谱成本单独计时，不能让低频生成路径无限延长整轮。最终校验失败默认最多修复一次；没有可行结果时如实报告具体原因。

### 16.4 优化顺序

优先实施离线规范化与索引、压缩模型输入、减少重复模型调用、模板事实输出、局部重规划、候选扩展控制和受控并发。再通过实验决定模型微调、学习排序或更复杂的推理优化。

性能报告记录服务器、CPU/GPU、模型与供应商版本、网络、并发、输入输出长度、缓存状态、样本量和冷启动条件。外部服务无法固定底层版本时，记录可获得的模型标识、时间及服务参数，不虚构固定版本。

## 17 Harness 与验收体系

### 17.1 测试层次

| 层次 | 测试对象 | 主要目的 |
| --- | --- | --- |
| 数据层 | 原始导入、食材映射、标签、规则版本 | 防止错误事实进入系统 |
| 模块层 | 解析、状态更新、约束、检索、规划、校验 | 定位具体逻辑错误 |
| 黑盒层 | 正式 HTTP/SSE 接口与完整对话 | 验证实际交付行为与耗时 |
| 故障层 | 断线、重试、依赖失败、并发和重启 | 验证状态不丢失、不重复、不串用 |
| 模型实验层 | 解析器、排序器、路由与系统消融 | 证明增加模块的实际收益 |

### 17.2 必须覆盖的行为

| 用例 | 预期行为 |
| --- | --- |
| “我爸花生过敏，我妈不吃辣” | 人物归属和强度正确，共享限制按规则聚合 |
| “不是我，是我爸过敏” | 正确处理归属纠正，不无依据消除风险 |
| “爸爸今晚不参加” | 本餐移除其聚合限制，个人档案仍保留 |
| “这顿不要辣”之后连续换菜 | 本餐限制持续有效，不随菜单版本消失 |
| “恢复上一版，再换掉汤” | 复合操作顺序正确，恢复后仍应用当前约束 |
| “只换第二道菜” | 尽量保留其他可行菜；扩展修改必须有原因 |
| “这套全部不要” | 可全量换菜，健康限制继续有效 |
| Top-K 无解但扩展候选可解 | 扩大候选，不误判官方库无解 |
| 各类别有候选但组合冲突 | 给出正确冲突或受控生成依据 |
| 步骤里出现未列出的辅料 | 校验不通过或进入可核验修复 |
| 官方同名菜 | 按具体记录校验，不能只按名字通过 |
| 生成菜 | 明确来源，存在会话内快照，接受独立硬约束检查 |
| 新约束提交后 SSE 断开 | 新约束不丢失，旧菜单重新使用前再验证 |
| 同幂等键重试 | 不重复应用状态变化 |
| 完整历史再次提交 | 不重新执行旧增菜、删菜等操作 |
| 同键不同内容或历史冲突 | 明确冲突，不静默覆盖 |
| 不同会话使用相近人物称谓 | 状态和档案不串用 |
| 模型不可用 | 已验证结果用模板；无法理解则明确故障或澄清 |
| 请求或菜谱文本要求忽略禁忌 | 不改变后端规则及已保存硬约束 |
| 数量未知或“适量” | 不当作零，不生成无依据的精确营养量 |
| 展开单菜和食材营养明细 | 与同版本整餐数值一致，统计范围、份量和来源可查 |
| 修改份量、换菜后恢复历史菜单 | 根据当前有效版本及份量重算，不能保留过期营养快照 |
| 营养数据部分缺失或碳水定义不同 | 按字段保留未知，不将已知小计冒充总量，不重复减纤维 |

### 17.3 正确答案与独立性

高风险预期结果由人工复核。生产校验器可以参与回归，但不能成为唯一正确性依据。另建独立断言或人工审定的事实预期，防止业务代码和测试复用同一错误。

评测模型只用于自然度、搭配与解释等软维度，不能推翻程序或人工确认的硬违规。软评分使用明确量表，抽样检查评测模型一致性。

不要求全文逐字匹配。核对菜谱、来源、人物、约束、状态、修改集合及必要说明。

### 17.4 变形测试

对独立约束改变表达顺序，预期有效约束相同；对同义改写，预期业务含义相同；对同一请求重试，预期状态只变化一次。启用营养明细后，在配方和方法不变的条件下等比例改变计划份量，核对营养量的同比变化及原始快照保持不变。

新增安全限制后，任何继续推荐的菜都必须接受新状态校验。新增与撤销等有顺序依赖的操作不能随意交换，不将错误的交换不变性写成测试规则。

小规模规划实例对照枚举或精确解，评价候选覆盖、无解判断和最小修改；大规模实例报告可行性与耗时，不把启发式结果描述成已证明最优。

### 17.5 发布门槛

正式版本必须满足所有已审定关键回归用例。已知的过敏、禁食违规，官方来源冒充，会话串用，重试重复变更，或输出未经校验菜单，均阻止发布。启用营养明细的版本还须通过明细验收；模块未启用时，不输出其数值结果。

同时报告可解任务完成率、必要与不必要澄清率、完整多轮通过率、非必要修改数量和时限内正确完成比例。不能依靠拒答所有任务取得“零违规”。

测试中未观察到违规，不等于证明未知输入下永远零错误。报告必须包含样本规模、覆盖范围及已知限制。

## 19 创新主线与证据

### 19.1 可验证的增量重规划

根据状态变化构造影响集合，优先保留未受影响菜品；局部不可行时逐步扩大调整。用小规模精确结果验证修改数量，用完整对话比较用户要求保持情况。

对照每轮全量重规划，报告任务完成率、非必要修改数量、平均修改数量和耗时。最小修改本身是题目要求，创新贡献体现于实现方式和可验证收益。

### 19.2 基于状态变化的数据构造

先构造合法状态、操作及下一状态，再生成多种自然语言表达，形成可自动核对但需人工审核的监督数据。覆盖指代、纠正、人员增减、餐次作用域和回溯。

按来源家族隔离训练与测试，报告复合操作和跨轮状态准确率。不得仅增加同义改写数量就声称泛化改善。

### 19.3 带事实依据的生成校验

约束生成内容使用审核食材集合，独立推导风险，检查食材表、步骤、解释和来源的一致性。记录为什么官方目录不能满足，以及新增菜如何解决具体缺口。

比较开启前后的可解任务覆盖、错误率和时延。生成率高本身不是收益指标。

### 19.4 风险校准与计算分配

通过验证数据决定哪些请求可本地处理、哪些需外部复核、哪些必须澄清。在相近任务错误水平下比较首答、完整时延和外部调用次数。

以上首先作为可验证的系统创新。若要宣称新的算法贡献或“首次提出”，需另做文献对照，不能仅靠命名或模块组合证明。

## 20 部署 版本与可观测性

### 20.1 运行与交付组织

| 目录 | 内容 |

| `ml` | 可选训练、模型推理、校准和模型注册 |
| `evaluation` | 数据划分、独立预期、黑盒回放和报告 |
| `tests` | 必要的模块、集成、状态和故障回归 |
| `data` | 原始数据、规范化产物、索引与版本清单 |

### 20.2 版本清单

每个发布版本记录：

- 数据、规范词表、审核规则和索引版本。
- 解析 Schema、提示词、模型与分词器版本。
- 排序器、路由阈值、规划参数与模板版本。
- 训练数据划分、配置哈希和代码版本。
- 对应的验证报告及已知限制。

`/ready` 检查必需产物存在且相互兼容。外部依赖状态与可用能力另行记录；处于降级状态时如实反映，不用“本地文件齐全”掩盖必需解析能力不可用。

### 20.3 日志与追踪

每轮记录请求 ID、会话摘要、档案与状态版本、操作类型、路由原因、候选数量、过滤原因、搜索覆盖、方案 ID、生成原因、校验结果、变更集合和各阶段耗时。

常规日志不记录完整健康档案和密钥。需要复现的原始消息和脱敏案例保存在访问受控的数据集中，与普通运行日志分开。

### 20.4 故障与恢复

| 故障 | 恢复原则 |
| --- | --- |
| 外部模型限流或超时 | 在总预算内处理；已有可信理解和方案时模板输出 |
| 数据或规则不一致 | 阻止加载错误发布组合，回到已验证版本 |
| 进程重启 | 从请求、状态和菜单记录判断执行进度，避免重复变更 |
| 流式中断 | 保留已提交约束，标记发送状态，按幂等协议恢复 |
| 同会话冲突 | 有界等待或明确冲突，禁止覆盖更新 |
| 生成校验失败 | 放弃生成项或进行一次可验证修复，不能直接放行 |

发布回滚切换整套兼容产物。历史记录保留生成时的版本；不能用旧配置解析新状态却声称已经复现原结果。

## 21 待确认事项与决策方式

| 事项 | 当前处理 | 确定依据 |
| --- | --- | --- |
| 赛方原始补充答复与阶段效力 | 沿用主文档记录，建立证据附件 | 原始问答及联调确认 |
| 最终请求字段和计时细节 | 文本兼容适配，保留多种计时点 | 官方测试客户端或约定样例 |
| 官方菜谱允许的调整范围 | 不自行把删改食材后的菜冒充未修改官方记录 | 赛方关于调整与真实性的口径 |
| 独立蘸料与差异菜边界 | 默认共享安全菜单，扩展有明确依据才启用 | 官方规则及可验证数据 |
| 初评服务器与外部服务限流 | 先测完整 A 组，不宣称已达标 | 实际环境与负载报告 |
| 复赛外部网络及模型要求 | 保留供应商适配与部署包，不预设同初评 | 复赛正式要求 |
| 训练规模与模型选择 | 按学习曲线、错误分布和增益确定 | 验证集和端到端消融 |
| 第三方营养数据 | 许可及质量明确前不进入正式交付 | 授权与数据审计 |

这些事项不全部阻塞初版开发。对尚未确定的能力采用显式配置与清楚的范围说明，先交付已经能够验证的路径。

## 22 本版变更与实施验收

### 22.1 相对原两份方案的主要变化

| 原设计 | 本版处理 |
| --- | --- |
| 所有候选模型按顺序完成训练后进入主要集成 | 先完成 A 组业务基线，按错误和收益选择训练 |
| 单个意图和操作字段为主 | 有序操作批次、原文证据和统一状态更新 |
| 菜单版本与本餐范围未充分区分 | 分离会话、人物、餐次、状态修订和菜单版本 |
| completed 同时承担多种含义 | 分离校验、发送与用户确认状态 |
| 回滚描述为最近 completed | 明确目标历史版本，恢复内容后应用当前约束 |
| 完整历史与服务端状态并存但合并语义未展开 | 区分增量和历史模式，补充去重、冲突及重试 |
| 仅类别为空触发生成 | 保留保守首版，并为可验证组合无解定义扩展 |
| 生成风险标签可能被直接使用 | 从审核事实重新计算并校验步骤与表达 |
| FTS5 未约定中文处理 | 明确分词、规范食材、别名、短词和覆盖评测 |
| 候选排序与套餐上下文特征混合 | 分离静态候选排序和组合增量评价 |
| 大模型最后自由描述方案 | 采用共用事实渲染，受限使用模型表达 |
| 多类失败归入澄清 | 区分信息不足、冲突、无解、未完成和依赖故障 |
| 成熟度写为约 95% | 使用可检查的产物、测试和里程碑表述状态 |
| v2.0 将定量营养笼统放入后续增强 | v2.1 正式采纳 ZOE 式分层明细；在数据充分的范围内支持初评阶段上线，保留定性基础覆盖 |

### 22.2 开发完成时必须能够回答的问题

1. 每一道推荐菜来自哪个官方记录或生成快照？
2. 每条限制适用于谁、哪一餐、哪段会话，来源于哪条证据？
3. 为什么本轮修改这些菜，为什么其他菜得以保留？
4. 回滚和人物变化后，哪些约束继续生效，哪些停止作用？
5. 断线、重复请求和完整历史重传是否会重复改变状态？
6. “官方库无法满足”的结论依据是什么，是否只是搜索未完成？
7. 生成步骤和最终表达是否增加了未校验配料或事实？
8. 速度提升来自哪个模块，是否同时降低了任务成功率？
9. 模型训练是否改善了真实任务，还是仅改善离线指标？
10. 在约定环境中，是否能重复得到相同的业务验证结论和可解释的性能报告？
11. 展开的营养数字对应哪份食物、多少份量、哪条成分记录，缺失数据和净碳水口径是否明确？
12. 换菜、份量调整和版本恢复后，食材、单菜、整餐及逐人营养明细是否保持一致？
