# 修复默认做法阻挡需求匹配，并接入明确做法请求

## 目的与实现

前次独立裁判的负意见暴露：用户未要求蒸/煮或多样性时，餐次/场景修复仍无条件保留旧做法；而明确“想吃蒸菜”没有一致的实际消费。本次分离这两种情况，不以默认方法分布冒充用户要求。

实现提交`d53f77fd770aa2f5efcdad0574362a543dda4020`；基线`bf20d9a98cb680cf0c04c84b345a50ac4102a195`。仅本地提交，不自动推送或合并。

- 有限明确正向做法、做法多样性进入源动作排序、有界同角色修复、建议及其他修复的覆盖保护。
- 未要求做法时不为保留旧蒸/煮或方法分布阻挡餐次/场景；明确多样性保护聚合覆盖与集中度，不冻结每一种旧方法身份。
- 只按原步骤的成菜动作消费；准备、设备、缓存方法标签不能冒充成菜参考。不从清淡/护心反推方法要求。
- 明确缺口、负向/未知/全部与冲突必须在回复中披露，不由最小模型事实选择隐藏。
- 保留不辣、过敏、已覆盖食材/口味/菜位场景、已知餐次、各定性目标、数量、指定槽位、空继续和重试边界。
