## 接入与默认状态

- `ALLOW_RECIPE_GENERATION=false` 默认关闭付费提案；仅有解析密钥不触发。Python设置与Compose参数都可显式启用，但本轮六次授权不代表生产持续调用已获授权。
- 已接 `create_app → MealAgent → 原菜单检索与核验 → 新提案 → 原menu_modify/rules → 会话持久化`。不是只在离线实验求解器中实现。
- 当初次原库规划被明确做法卡住，可用已核验新提案与原安全候选重试同一规划器；不撤销菜数/汤数、做法或食材限制。已有菜单优先限定蛋白主体位修补；局部更换不改其他完整菜；只读/继续不能新造菜。
- 原库适配豆腐优先；排序遗漏、拒绝一菜不直接当库无菜。严格库存、豆类过敏、耗时未知等原边界保留。
- 新配方只留所属服务端会话，重启可复原，不注入共享2000库。请求不能提供生成记录；公共会话状态不泄漏服务端存储映射。

## 输出与安全

模型只提出 `RecipeDraft`（名称、公开原料、简短步骤），不接受模型提供的源行、ID、标签、安全决策、营养或健康功效。规范化、身份摘要、角色/完成做法和已知限制均本地执行。JSON外层明确规定 `draft`，兼容首轮精确三个字段的直接对象，不放宽额外字段。

原生/兼容/SSE保留“生成提案、非原2000、待试做、空源行、用量/份数/营养/设备参数未知”说明；模型生成失败只尝试既有基础提案，仍不能用蒸替明确炒/煎/焖要求。

当前有限公开原料白名单，主要服务豆腐主体补缺；不是所有食材的通用造菜。没有称盐/酱油出现即高钠，也没有编护心、降压治疗或份量营养事实。

## 真实实验与费用

同一账本用户批准最多6次：5次HTTP收到、1次连接失败也保守计额度，已停止。无自动重试、无AI评审或解析收费。固定公开自编需求、固定公开原料名单送Flash；原2000、菜单、官方/私有档案不送。实际响应模型名为 `deepseek-flash`，不用名称推断模型版本或质量。

最初失败原件保留：首轮G01外层格式拒用、跨TestClient复用连接池导致G05连接失败；后续仅在剩余4次额度内续跑，每个事件循环独立创建和关闭HTTP客户端。不是重置预算重新跑6次。
