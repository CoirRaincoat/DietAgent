## 1. 目标与当前范围

未配置档案时默认本地2000条原菜谱＋3个合成用户（900001–900003）；显式`LOCAL_PROFILE_PATH`按源id1–50查本地档案，不加载官方对话、不合并演示用户。original资料保本地，模型仅收用户文本和白名单结构，解释facts及助手历史不外发。不能随机匹配画像或把所有ID映射到一人；本轮只MockTransport，真实模型理解/平台/干净部署仍未验。

主办方截图按官方1–50整数ID准备，简短“是的”不是完整协议，Key参赛方自备。脱敏源字段`id`，启动严格50唯一整数不缺号；未配1–50为404，配置后允许仅用户文本解析而非外发档案。Key/档案不纳公开包，见[LOCAL_OFFICIAL_IDS.md](LOCAL_OFFICIAL_IDS.md)。

当前不计算每人精确营养摄入、份量、医疗功效或可保证的整餐耗时。允许人数1–8、总菜数1–8、汤数0–3（以实际schema与业务一致性核验为准）；总菜数包含汤。当前不是多日计划或后台通知服务。

## 2. 架构及数据来源

FastAPI模块化单体，入口`app.api.main:app`。`load_runtime_catalog`选择未配置的合成目录或显式本地50档案，沿用原CSV读取，标准化原料/步骤/类别但不改原文件；稳定ID与源行/指纹可回溯。同名不同配方保不同身份，规划仍做名称去重。标签缺失不是任意补功效的依据；助手参考与原标签分开，有原方绑定的参考才用于匹配。

## 3. 两类调度算法

### 请求调度与状态一致性

`app/api/main.py`用进程内容量8的Semaphore保护请求，最多等待0.25秒获取容量，超时返回429。服务层对同一会话串行处理；持久层用版本条件更新，防跨用户复用。首轮request_id可派生稳定session ID；同请求同版本重试返回缓存，复用ID换消息或过期重放返回冲突。普通解释/继续不因软指标重排。

此实现不是分布式队列：必须单worker；没有完整进行中请求崩溃恢复、跨进程一致性或exactly-once承诺。无鉴权的本机Demo不能直接开放公网。

### 排菜调度：实际默认路径

1. 读取档案和会话，解析本轮增量意图，有限原文守护核对数量、约束归属与撤销权限。
2. 合并当前参餐者的过敏、不辣、排除食材等全桌限制；缺关键信息/未知过敏/矛盾时先澄清，不能用默认值当确认。
3. 全库词法检索排序，再筛实际规则、成菜资格与明确限制；不是LLM自由生成菜名，不在这里新增向量数据库或扩池。
4. 在允许候选中保留仍合法旧菜、填指定槽位与汤位。初选比较成菜角色、明确方法/餐次参考、搭配参考、已有规则软分、检索及稳定去重因素，随后做有界同角色修复。
5. 现行修复包括食材覆盖、餐次、荤素主体参考、明确方法、口味/场景和健康定性参考。明确要求与权限优先于内部代理；旧做法频次并非用户指令，不能要求所有软指标都不下降。
6. `b1d4acb`在末段加入多人有汤正餐的粥位调整：人数至少3、午晚餐、已有汤且未点名要粥时，可用已有安全同角色熟米饭候选替换粥。保已覆盖食材、明确方法/数量、餐次、口味/场景与指定换菜范围；无候选保留，不禁粥、不推断营养或份量。小修不是新求解器。
7. 最终再次核验菜数、汤数、身份/去重、硬规则、明确荤素数量及必需的菜位/食材做法；失败不输出未经核验的新菜单。随后按原始记录构造卡片、定性来源解释、缺口和警示。

是确定性的有界启发式规划，不保证全局最优、全库无解或医学适用性。默认API启用已有同ID最近8份有效推荐历史：明确肯定的新餐命令才释放旧整餐、沿用饮食限制，同等适配下参考近期名称；普通继续/解释/重试/疑问/否定/局部换菜不扩权限。历史不是实际食用，第四餐仍重复2道，不承诺完全不重复。直接构造MealAgent保旧兼容False；内容多样性实验、初选frontier及CP-SAT仍未启用，不能把离线工具写成默认收益。

### 硬约束与软参考

过敏、不辣、明确素食模式、明确数量、用户/会话所有权及局部换菜权限不得被加分抵消。品牌完整配料、漏列食材及交叉接触无法由文本穷尽，未知成分需保护/澄清而非猜安全。健康目标是有完整原方依据的定性偏好，不是硬性摄入阈值。

健康解释同时保原盐、糖、含钠调味品等风险，不因少量蔬菜/谷物辅料把整道菜评成“护心高分”。源未提供份量或可靠成分表时保未知；不编蛋白質克数、低钠标签、降压治疗或每人够吃结论。内部代理分不进入API作为质量自评。

## 4. Prompt策略及模型边界

`configs/intent_prompt.txt`和运行时`Intent` schema约束解析。仅用户消息/用户历史与白名单结构，档案不发模型；用户文字视为数据而非指令权限。只提本轮增量，不生成菜谱/营养/诊断，区分过敏/不喜欢、人数/菜数、总菜/汤数、人物/全桌，保否定及安全限制。

DeepSeek适配器采用JSON模式，关闭thinking，temperature=0、max_tokens=1600、非流式上游请求；这些是当前实现参数而非模型质量保证。响应核验完整stop、非空JSON、重复键/非法数、schema及语义。服务端再核状态与原文，不只相信Prompt。参数由环境指定，密钥SecretStr，不写日志或传前端。

当前synthetic/original均仅在本地提供约束；解析正向白名单不发profile、constraints、diners、菜单ID/原料/菜名、assistant/tool/system历史、生成澄清/口味撤回原文。只发当前及最近6条用户文字、字段类型/布尔状态、菜单槽号及固定取舍选项。本地完整状态保留供语义与安全核验；用户自己输入的健康/菜名仍会发送，不能称零健康信息或自动匿名。源only短回复可能信息不足须明确指代，真实NLU未验。见`USER_ONLY_MODEL_BOUNDARY.md`；旧403证据不重写。

默认DeepSeek.explain直接本地返回全部事实ID，无HTTP；服务渲染同一核验模板，标记verified_template，不误报模型失败。原程序/风险等必保事实不丢，菜名/配料/步骤不改写；解析失败502/503不伪装成功。本轮用真实适配器＋假HTTP固定Intent，不代表真实NLU/TTFT已测。

## 5. 通知与提示生成机制

此处“通知”指本轮接口的用户提示，不是定时任务、短信、微信或外部推送：

| 类型 | 来源与生成 | 输出与边界 |
| --- | --- | --- |
| 信息不足/歧义 | confirmed/pending fields、人物归属、数量一致性 | clarification_questions与reason；未确认不排菜 |
| 无可行菜单 | 实际候选、最终规则或范围失败 | no_feasible_menu；不展示旧失效菜单，也不称穷尽全库无解 |
| 菜谱/健康/数据缺口 | 入选原记录、目标证据、未知配料/份量、未覆盖偏好 | warnings、nutrition_analysis、已核验事实；不编疗效 |
| 推荐解释 | response_copy.response_facts及必选ID | 原生完整JSON、兼容文本；本地确定性顺序，不发解释API |
| 运行失败 | 统一异常映射 | HTTP错误码及安全消息，不回显密钥/上游完整请求 |

模块见`app/agent/clarification.py`、`app/agent/response_copy.py`、`app/api/presentation.py`及`app/api/openai_compat.py`。后台通知机制未实现；若比赛要求必须外部通知，需补确切协议/权限，不能用文本提示冒充。

## 6. 测评API与部署

原生`POST /chat`返回schema_version=2.0业务JSON；兼容`POST /v1/chat/completions`仅接受一条user纯文本增量、`model=fangtai-meal-agent`与明确user ID，可非流式/SSE。多轮用返回session；request_id用于幂等，链路X-Request-ID不是幂等键。平台确切入参未提供，不能保证任何OpenAI完整客户端都兼容，详见[API](API.md)。

SSE在解析、规划、最终安全核验完成后分块输出核验文本，不直接转发模型token。Server-Timing/timings_ms是服务阶段耗时，非客户端TTFT；平台需性能测量时使用已有`evaluation.stream_performance`，真实付费调用须另授权。

源码部署使用锁依赖、单worker Uvicorn；Docker后端Python3.13及非root用户，前端Nginx提供本机8080并关闭SSE缓冲，SQLite卷保会话。更新源码需重建镜像；缺密钥的健康页正常不表示模型可推荐。干净环境/依赖/当前容器的验证状态见[交付计划](DELIVERY_PLAN_20261007.md)，旧部署PASS不代表当前候选通过。
